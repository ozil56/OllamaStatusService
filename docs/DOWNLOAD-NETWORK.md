# Automatic model download networking

OSS 1.6.1 automatically routes model downloads on the **target OSS server**. Users continue to download from `/manage`; there is no proxy switch in the browser and no need to change the server's TUN mode. Install the complete package on each target node that needs this support.

The installer connects Ollama's `HTTPS_PROXY` to a loopback-only CONNECT relay inside the existing OSS gateway. The relay checks the original installing user's `HTTPS_PROXY` / `ALL_PROXY`, machine environment, enabled Windows Internet Settings proxy and any proxy retained from the previous backend service. HTTP CONNECT, HTTPS proxies and SOCKS5 with remote DNS are supported. Settings are refreshed for new connections; established downloads keep their connections. No system-wide proxy or DNS settings are changed.

If no configured proxy can be reached, the relay connects through the current network, including the existing TUN. For known model domains (`ollama.com`, `ollama.ai`, `hf.co`, `huggingface.co`, `r2.cloudflarestorage.com` and their subdomains), it accepts Fake-IP addresses in `198.18.0.0/15`. Other destinations must resolve entirely to public addresses. Resolution is checked once and the checked address is used to connect. Local, private, link-local and metadata addresses remain blocked. The relay only accepts HTTPS CONNECT to port 443 and listens on `127.0.0.1`, with no new firewall opening.

TLS remains end to end between Ollama and the model server. OSS neither decrypts downloads nor installs a root certificate, disables certificate checks, sets `insecure`, or changes HTTPS to HTTP. HTTPS proxy certificates are also verified. An explicit proxy authentication/access denial or a proxy certificate error is reported rather than bypassed.

This requires an Ollama release that supports proxies in its protected transfer transport; the verified baseline is **0.40.9**. `/status.download_network.requires_ollama_update` identifies older versions. Use the OSS tray's Ollama updater while idle when necessary. The relay does not silently upgrade Ollama or restart services. Network setting changes only affect new connections. OSS/Ollama upgrades refuse active or uncertain work, including unfinished uploads and relay connections; upgrading from OSS 1.5.0 or newer closes new admission before the final idle check. Older OSS releases do not implement that gate: pause submissions and arrange an idle window for their initial upgrade.

The fallback needs a working TUN mapping or direct route. It cannot create Internet connectivity, repair an expired proxy subscription, or bypass proxy login/access restrictions. PAC scripts, unexposed application-internal proxies, custom Fake-IP ranges and private registries are not automatically supported; the built-in path still works if the current network routes the supported model domains. Errors appear in the download task and `/status.download_network.last_error`; credentials and proxy URLs are not included in that status.

The generated `download-network.json` is local installation state. It contains the relay port, original user's SID and optionally a preserved upstream proxy; keep it out of public packages. Official Ollama upgrades back it up and verify it along with the existing service configuration. OSS upgrades preserve its upstream settings and choose a free loopback port again.

Verification: `tests/download_network_checks.py` uses real TCP, CONNECT, SOCKS5 and TLS, with Fake-IP DNS/dial behavior injected only in the test process. It never changes the host's DNS, trust store or TUN mode. The update guard suite verifies relay connections prevent an automatic stop. These isolated tests do not certify every third-party TUN driver.
